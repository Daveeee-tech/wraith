# Offramp order access

An offramp order carries a bank payout amount, a deposit address and a rate, so
reading one back requires proof of having created it.

## Creating an order

`POST /offramp/orders` returns two values the client must keep:

| Field         | Example                                      | Notes |
| ------------- | -------------------------------------------- | ----- |
| `id`          | `ofr_` + 22 URL-safe characters (128 bits)   | The id to look the order up by. Not the provider's id, which is never returned. |
| `accessToken` | `oft_` + 43 URL-safe characters (256 bits)   | Bearer credential. Shown once; only its SHA-256 is stored. |

The response is sent with `Cache-Control: no-store`.

## Reading an order

```bash
curl -H "Authorization: Bearer $ACCESS_TOKEN" \
  https://<host>/offramp/orders/$ORDER_ID
```

| Status | Meaning |
| ------ | ------- |
| `200`  | The token belongs to this order. |
| `401`  | No usable `Authorization: Bearer` header. Identical for every id. |
| `404`  | Unknown id, malformed id, or a token that does not belong to the order. These are deliberately indistinguishable. |
| `429`  | Too many failed lookups from this IP. |

Only failed lookups count toward the limit, so polling your own order never
consumes it. Defaults: 10 failures per 15 minutes per IP.

| Variable                       | Default  | Purpose |
| ------------------------------ | -------- | ------- |
| `OFFRAMP_LOOKUP_MAX_FAILURES`  | `10`     | Failed lookups allowed per window. |
| `OFFRAMP_LOOKUP_WINDOW_MS`     | `900000` | Window length. |

## Retrying a creation

Replaying `POST /offramp/orders` with the same `idempotencyKey` and
`walletAddress` returns the same order (`replayed: true`) with the same `id` and
a **new** `accessToken`; the previous token stops working. A different
`walletAddress` gets `409` and nothing about the order. Idempotency keys should
therefore be random and generated by the client.

## GET /offramp/rate — `coin`, and how it becomes required

```
GET /offramp/rate?coin=xlm   → 200 { coin: "xlm",  rate: <NGN per 1 XLM>,  indicative: true }
GET /offramp/rate?coin=usdc  → 200 { coin: "usdc", rate: <NGN per 1 USDC>, indicative: true }
GET /offramp/rate            → 200 { coin: "usdc", … }  + a deprecation log line
GET /offramp/rate?coin=doge  → 400
GET /offramp/rate?coin=      → 400
```

`rate` is naira per **one unit of the coin named**, never naira per dollar, and
it comes from `ngnPerCoin()` — the same path the onramp quotes with, so the two
rails cannot disagree. The response always carries the coin it was priced for.

Pricing a coin as dollars is the defect that cost real money on the onramp: ₦1,000
bought 0.6 XLM instead of 3.6, because a dollar rate was divided as though it
were an XLM rate. So `coin` is on its way to being mandatory.

### Why a missing coin is still answered

Because installed APKs cannot be updated from this repository. The mobile client
asks `isOfframpAvailable()`, which calls this endpoint and reads **any** error as
"cash-out is down" and hides the tile. A 400 on a coin-less request therefore
does not tell anyone to pick a coin — it removes cash-out for every user on an
older build, silently, and looks like an outage. #216 was this mistake, and the
lesson recorded from it was: ship the client first.

Answering is not the silent defaulting this endpoint exists to prevent. A USDC is
a dollar, so the USDC rate *is* the number a coin-less caller gets from today's
deployment: unchanged for the callers that cannot change yet, wrong for XLM in
exactly the way it is already wrong, and now labelled with the coin it is priced
for so a client can see the difference.

### The three stages

1. **Here.** An unknown coin 400s — new behaviour, nothing depends on it. A
   missing coin is answered as `usdc` and logged as deprecated, once per
   User-Agent, so the log reads as a list of callers rather than a flood.
2. **Clients.** Both wallet builds send `coin` on every rate call, including the
   availability check — which should probe with an explicit coin, or better a
   health route, because "is the service up" and "what is the rate for XLM" are
   different questions and one endpoint should not be forced to answer both.
3. **Then.** When a build carrying stage 2 is actually released **and** the
   deprecation line has been quiet for a full release cycle, a missing coin 400s
   and `logCoinlessRateRequest` is deleted along with the compatibility default.

Stage 3 is a breaking change to a money-moving endpoint. Do not make it from the
server side alone: it needs evidence from the log, not a judgement that enough
time has passed.

## Upgrading

- Orders created before this change have no `id` or token and cannot be read
  through `GET /offramp/orders/:orderId`. Replaying their creation request
  (same key and wallet) issues them credentials.
- The lookup response now reports `source: "live"` instead of `"linq"`.
- Two nullable columns were added to `OfframpOrder` (`publicId`,
  `accessTokenHash`); run `npx prisma db push`.
